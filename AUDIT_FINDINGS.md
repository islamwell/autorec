## 🚨 CRITICAL ISSUES

### 1. **Audio Buffer Contains Decibel Levels Instead of Waveform Data**

**Location:** `/lib/services/keyword_detection/keyword_detection_service_impl.dart:379-432`

**Severity:** CRITICAL - Complete failure of MFCC-based detection

**Description:**
The real-time keyword detection is fundamentally broken. The audio buffer stores normalized decibel values (loudness measurements) instead of actual audio waveform data. MFCC extraction requires the raw PCM audio signal to perform FFT and extract spectral features.

**Problem Code:**
```dart
// Line 379-384: Stores decibel values
void _processAudioLevel(double decibels) {
  final normalizedLevel = _normalizeDecibels(decibels);
  _audioBuffer.add(normalizedLevel);  // ❌ Wrong! This is just loudness
}

// Line 422-432: Tries to extract MFCC from decibel values
final recentAudio = _audioBuffer.sublist(...);
final recentMfccFeatures = _mfccExtractor.extractFeatures(recentAudio);  // ❌ Can't extract frequency info from decibels
```

**Impact:**
- **Training works**: Reads actual WAV file and extracts proper MFCC features
- **Detection fails**: Tries to match MFCC features against decibel-level "features"
- **Result**: Keywords will NEVER be properly recognized in real-time

**Why This Happens:**
- Flutter Sound's `onProgress` events only provide decibel measurements, not raw audio samples
- The code architecture assumes we can get streaming audio data, but `flutter_sound` doesn't expose this easily for continuous listening

**Recommended Fix:**
Two options:

**Option A - Chunked File Reading (Easier, Higher Latency)**
1. Record audio in small chunks (e.g., 500ms WAV files)
2. After each chunk completes, read the file and extract MFCC
3. Compare against trained keyword
4. Continue with next chunk
- Latency: ~500-1000ms
- Reliability: High

**Option B - Raw Audio Stream (Better, Complex)**
1. Use platform-specific code to capture raw PCM samples
2. Stream actual audio data (not just decibels)
3. Extract MFCC from raw samples
4. Real-time comparison
- Latency: ~100-200ms
- Reliability: High (after implementation)
- Complexity: Requires native code (Kotlin/Swift)

## ⚠️ HIGH PRIORITY ISSUES

### 2. **WAV File Parsing Assumes Fixed Header Size**

**Location:** `/lib/services/audio_features/mfcc_extractor.dart:301-322`

**Severity:** HIGH - May fail on non-standard WAV files

**Description:**
The WAV parser assumes a fixed 44-byte header, but WAV files can have variable-length headers with additional chunks (e.g., LIST, INFO, metadata).

**Problem Code:**
```dart
// Line 302: Hardcoded header size
const headerSize = 44;
final audioData = wavData.sublist(headerSize);  // ❌ May skip audio data or include header
```

**Impact:**
- Works for simple WAV files generated by the app
- May fail for WAV files from other sources
- Could read incorrect data if header is larger than 44 bytes

**Recommended Fix:**
Parse WAV header properly:
```dart
// Find "data" chunk by searching for the marker
int findDataChunk(Uint8List wavData) {
  for (int i = 0; i < wavData.length - 4; i++) {
    if (wavData[i] == 0x64 &&      // 'd'
        wavData[i+1] == 0x61 &&    // 'a'
        wavData[i+2] == 0x74 &&    // 't'
        wavData[i+3] == 0x61) {    // 'a'
      return i + 8;  // Skip "data" marker and size field
    }
  }
  return 44;  // Fallback to standard size
}
```

### 3. **FFT Recursive Implementation May Cause Stack Overflow**

**Location:** `/lib/services/audio_features/mfcc_extractor.dart:349-396`

**Severity:** MEDIUM-HIGH - Potential crash on large audio

**Description:**
The FFT uses recursive divide-and-conquer, which can cause stack overflow for large frame sizes or many repeated calls.

**Problem Code:**
```dart
List<Complex> transform(List<Complex> input) {
  final evenFFT = transform(even);  // Recursive call
  final oddFFT = transform(odd);    // Stack depth = log2(n)
}
```

**Impact:**
- Current frame size (512) is safe: log2(512) = 9 stack levels
- If frame size increases to 2048: log2(2048) = 11 levels
- Repeated calls may accumulate stack pressure

**Recommended Fix:**
Implement iterative FFT using bit-reversal permutation (Cooley-Tukey algorithm).

## ⚠️ MEDIUM PRIORITY ISSUES

### 4. **Memory Leak Risk - Audio Buffer Unbounded During Detection**

**Location:** `/lib/services/keyword_detection/keyword_detection_service_impl.dart:384-394`

**Severity:** MEDIUM - Memory leak over time

**Description:**
While the buffer has a max size check, the buffer is cleared after detection (line 466) but continues growing again. Over hours of background listening, this could accumulate.

**Current Code:**
```dart
_audioBuffer.add(normalizedLevel);
if (_audioBuffer.length > _maxBufferSize) {
  _audioBuffer.removeAt(0);  // ✓ Good, but slow for List
}
```

**Recommended Fix:**
Use a proper circular buffer or `Queue` for O(1) operations:
```dart
import 'dart:collection';
final Queue<double> _audioBuffer = Queue();

// Adding
_audioBuffer.add(value);
if (_audioBuffer.length > _maxBufferSize) {
  _audioBuffer.removeFirst();  // O(1) instead of O(n)
}
```

### 5. **No Error Handling for MFCC Extraction Failures**

**Location:** `/lib/services/keyword_detection/keyword_detection_service_impl.dart:422-475`

**Severity:** MEDIUM - Silent failures

**Description:**
MFCC extraction is wrapped in try-catch but errors are only logged. No user notification or recovery strategy.

**Impact:**
- User doesn't know detection has failed
- System continues running but not detecting
